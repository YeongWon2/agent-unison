# Agent Unison 개발 계획 초안

이 문서는 동기화 제품 설계를 논의하는 초안과 승인된 기반 구축 작업을 구분한다. 동기화 엔진의 추천안은 아직 승인된 제품 명세가 아니다.

## 승인된 현재 작업

계획 구체화, Claude·Codex 플러그인 기본 구조, 버전·릴리즈 CI 구축, 검증 후 push까지 수행한다. 동기화 엔진 구현과 실제 릴리즈 발행은 이번 작업에 포함하지 않는다.

기본 구조는 `plugins/agent-unison/`의 두 manifest가 같은 `skills/`를 사용하도록 만든다. 첫 스킬은 동기화 범위를 조사하고 계획하는 기능만 제공한다. 존재하지 않는 동기화 명령을 안내하지 않는다.

개발 검증은 Node.js 24 이상과 표준 라이브러리로 수행한다. 런타임·개발 npm 의존성을 추가하지 않는다. GitHub Actions는 공식 checkout·setup-node와 Release Please Action을 확인한 SHA로 고정한다. 버전은 `version.txt`를 기준으로 두 plugin manifest와 Release Please manifest의 일치를 검사한다. 릴리즈 방식과 설정 조건은 [릴리즈 운영 문서](RELEASING.md)에 기록한다.

### 실행 순서

- [x] 기본 구조: 두 marketplace·두 plugin manifest·계획 스킬을 작성하고 실제 플러그인 검증기로 확인한다.
- [x] 검증: 정상 패키지 통과, 버전 불일치·누락 파일·잘못된 경로·릴리즈 설정 누락 거부를 테스트하고 검사기를 구현한다.
- [x] CI: 모든 브랜치 push·PR 검증과 main의 Release Please 흐름을 연결했다. 두 workflow의 actionlint 검증을 통과했다. 원격 실행 확인은 다음 항목에서 다룬다.
- [x] 문서: 설치법·현재 지원 범위·버전 정책·릴리즈 설정·실패 시 대응을 작성했다. 로컬 링크와 플러그인 검증기로 확인한다.
- [ ] 원격 검증: 작업 브랜치를 push하고 GitHub Actions 결과를 확인한다. main 반영과 Actions PR 생성 권한 변경은 구체적인 결과를 제시한 뒤 확인한다.

변경 파일은 `.claude-plugin/marketplace.json`, `.agents/plugins/marketplace.json`, `plugins/agent-unison/**`, `scripts/validate.mjs`, `scripts/validate.test.mjs`, `.github/workflows/ci.yml`, `.github/workflows/release.yml`, `release-please-config.json`, `.release-please-manifest.json`, `version.txt`, `package.json`, `README.md`, `CHANGELOG.md`, `.gitignore`, 이 문서와 `docs/RELEASING.md`다.

테스트는 임시 저장소 fixture를 만들고 `node scripts/validate.mjs <fixture-root>`를 실제 프로세스로 실행한다. 정상 입력의 종료 코드 0을 먼저 실패 상태에서 확인한 뒤 검사기를 구현한다. 이후 버전 불일치·잘못된 경로 등의 입력을 하나씩 추가해 거부 동작을 검증한다. 전체 검증 진입점은 `npm run check`다.

## 해결할 문제

Claude Code와 Codex를 함께 사용할 때 스킬·작업 규칙·참고 문서를 따로 관리하면서 내용이 어긋나는 문제를 줄인다. 같은 파일을 배포하는 것뿐 아니라 각 도구가 그 파일을 발견하고 사용할 수 있는지 확인하는 것이 목적이다. 모델의 응답이나 지시 준수까지 동일하게 만드는 것은 보장할 수 없다.

사용자가 밝힌 요구는 다음과 같다.

- 제품 이름은 Agent Unison이며 저장소는 `git@github.com:YeongWon2/agent-unison.git`이다.
- Claude와 Codex의 스킬·문서 등을 동기화하는 플러그인을 만든다.
- `im-ian/agent-handoff`는 참고 자료이며 그대로 따를 설계가 아니다.
- 구현에 앞서 계획서를 작성하고 접근 방식을 논의한다.

한 컴퓨터와 여러 컴퓨터 중 어느 범위를 먼저 지원할지, 사용자 전역과 프로젝트 중 어느 위치를 먼저 다룰지는 아직 정하지 않았다.

## 공식 문서에서 확인한 제약

| 항목 | 확인한 사실 | 계획에 주는 영향 |
| --- | --- | --- |
| 스킬 위치 | Claude Code는 `.claude/skills/`, Codex는 `.agents/skills/` 등의 위치에서 로컬 스킬을 탐색한다. | 두 도구의 출력 위치를 명시적으로 구분한다. 파일 복사 이후 실제 발견 여부도 검증해야 한다. |
| 지침 파일 | Claude Code는 `CLAUDE.md`와 `@path` import를 지원한다. Codex는 `AGENTS.md`, `AGENTS.override.md`, 설정된 대체 파일명 등의 탐색 규칙을 사용한다. | 파일명을 바꾸거나 import 문장을 그대로 복사하는 것으로 호환성을 판단하지 않는다. |
| 적용 범위 | 지침과 스킬의 탐색은 디렉터리 위치와 도구별 규칙에 영향을 받는다. | 전역 지침을 프로젝트로 옮기거나 하위 경로 규칙을 전역 본문으로 펼치지 않는다. |

근거: [Claude Code skills](https://code.claude.com/docs/en/skills), [Claude Code memory](https://code.claude.com/docs/en/memory), [Codex skills](https://developers.openai.com/codex/skills), [Codex AGENTS.md](https://developers.openai.com/codex/guides/agents-md). 플러그인 패키지 내부 경로와 일반 로컬 스킬 경로는 별도로 검증한다. 지원 버전은 설치·실행 실험을 거쳐 정한다.

## agent-handoff에서 가져올 것과 재설계할 것

README는 기기별로 Claude·Codex 스냅샷을 분리해 저장하고, `pull`이 현재 프로필의 스냅샷만 읽으므로 서로 다른 프로필 사이의 pull을 차단한다고 설명한다. 이 구조는 기기 간 이동에 초점을 두며, Claude ↔ Codex 변환 기능의 근거가 되지는 않는다. 아래 평가는 README 범위이며 소스 코드 전체 감사 결과가 아니다. [참고 README](https://github.com/im-ian/agent-handoff#readme)

| 항목 | 평가 | Agent Unison 제안 |
| --- | --- | --- |
| 적용 전 diff | 사용자가 덮어쓸 내용을 확인할 수 있다. | 변경 계획을 먼저 만들고 검토한 계획만 적용한다. |
| 기기 경로 토큰화 | 여러 기기에서 절대 경로가 달라지는 문제를 다룬다. | 여러 기기를 지원할 때 명시적인 경로 바인딩을 검토한다. 임의의 문서 문자열을 일괄 치환하지 않는다. |
| 허용 목록·민감정보 검사 | 전송할 파일을 제한하는 데 참고할 수 있다. | 사용자가 선택한 자산만 관리한다. 전송 기능은 별도 범위로 다룬다. |
| 프로필별 스냅샷 | 서로 다른 도구의 파일을 섞지 않는 목적에는 맞지만 도구 사이의 의미 차이를 해결하지 않는다. | 공통 내용과 도구별 내용을 구분하는 표현을 설계한다. |
| Git hub와 push/pull | 기기 간 배포에는 유용하지만 첫 버전에 포함하면 인증·원격 충돌·전송 정책까지 다뤄야 한다. | 로컬 변환과 파일 적용을 먼저 검증한 뒤 전송 계층 추가를 결정한다. |

Agent Unison이 단순 복사만 제공한다면 사용자가 Git이나 수동 링크 관리 대신 설치할 이유가 약하다. 차별점은 관리 대상 선택, 도구별 출력, 충돌 검출, 호환되지 않는 항목의 설명에 두는 안을 추천한다.

## 원본 관리 방식 비교

| 방식 | 이점 | 비용·한계 | 현재 판단 |
| --- | --- | --- | --- |
| 공통 원본 → Claude·Codex 출력 | 같은 사실을 한 곳에서 수정하고 결과를 재현할 수 있다. 충돌의 기준도 명확하다. | 원본을 편집하는 새 작업 방식이 필요하다. 기존 파일을 가져오는 절차가 필요하다. | 추천안. 첫 구현의 충돌 처리 범위를 줄인다. |
| Claude 또는 Codex 한쪽을 원본으로 지정 | 현재 사용 중인 파일을 계속 편집할 수 있다. | 원본 도구의 기능에 종속되고, 다른 도구만의 규칙을 따로 보관해야 한다. | 가져오기 시작점으로 활용한다. 장기 공통 원본으로 삼는 것은 보류한다. |
| Claude ↔ Codex 양방향 병합 | 양쪽에서 직접 고치는 흐름을 유지할 수 있다. | 동시 수정·삭제·변환 손실·기준 버전 관리가 필요하다. 텍스트 병합이 의미 보존을 보장하지 않는다. | 첫 버전에서는 보류한다. 실제 사용에서 필요성이 확인되면 재검토한다. |

추천안의 비용은 사용자가 원본 위치를 배워야 한다는 점이다. 대신 자동 병합과 LLM 변환을 기본 경로에서 제외해 결과를 재현하고 검증하기 쉬워진다. 개발 시간·운영 비용·정확성 사이에서 정확성과 관리 비용의 예측 가능성을 우선하는 제안이다.

## 첫 버전 범위 제안

시작 범위는 한 컴퓨터의 한 프로젝트를 추천한다. 프로젝트 파일만으로 설치·diff·충돌·복구를 검증한 뒤 사용자 전역으로 확대한다. 사용자 전역 관리가 핵심 사용 사례라면 이 순서를 바꾼다.

| 자산·기능 | 제안 범위 | 조건 |
| --- | --- | --- |
| 스킬 | 사용자가 고른 `SKILL.md`와 필요한 `references/`, `scripts/`, `assets/` | 상대 경로와 실행 파일 속성을 보존한다. 외부 의존성이 있으면 보고한다. 동기화가 스크립트를 실행하지는 않는다. |
| 공통 지침 | 루트 `CLAUDE.md`·`AGENTS.md`에 반영할 공통 내용 | 도구별 내용과 기존 사용자 작성 부분을 보존한다. 관리 구간의 식별·수정 규칙은 실험으로 확정한다. |
| 참고 문서 | 사용자가 선택한 Markdown과 로컬 참조 파일 | 저장된 문서와 자동 로드되는 지침을 구분한다. 일반 문서를 임의로 시작 지침에 추가하지 않는다. |
| 호환성 검사 | 탐색 경로·메타데이터·도구 전용 지시·누락 참조 | 자동으로 의미를 바꾸지 않는다. 수동 조정이 필요한 항목을 보여준다. |
| 로컬 상태 | 변경 미리보기·충돌 검출·백업·복구 | Agent Unison이 관리한 범위를 기록한다. |

hooks, MCP 연결, 인증 파일, 권한 설정, 자동 memory, 대화·세션 이력, 설치된 플러그인 캐시, 하위 디렉터리별 지침 변환은 첫 버전 추천 범위에서 제외한다. 단순 문서 동기화와 다른 실행·권한·범위 의미가 있기 때문이다. 기존 스킬에 해당 기능이 필요하면 조용히 제거하지 않고 미지원 항목으로 보고한다.

여러 컴퓨터 지원은 독립된 추가 단계로 둔다. 공통 원본의 Git 버전 관리와 원격 push/pull 자동화는 구분한다. 원본 저장소를 사람이 Git으로 이동할 수 있더라도 제품이 전송·충돌 처리를 지원한다고 표현하지 않는다.

## 추천 구조와 데이터 흐름

플러그인은 사용자 의도를 받아 동일한 로컬 실행 엔진을 호출하는 진입점으로 둔다. 파일 계산·diff·적용은 엔진이 맡고, Claude와 Codex의 플러그인 형식과 호출 방법은 각 진입점이 맡는다. 언어·패키지 관리자·배포 방식은 아직 결정하지 않는다.

```text
선택한 기존 스킬·문서
        │ 명시적으로 가져오기 + 검토
        ▼
공통 원본 + Claude 전용 내용 + Codex 전용 내용
        │ 검증 / 대상별 변환
        ▼
변경 계획(diff, 호환성 문제, 충돌, 적용 전 파일 해시)
        │ 검토한 계획 적용
        ▼
Claude 출력 / Codex 출력 + 로컬 적용 기록·백업
```

출력 파일에서 발견한 수정은 자동으로 원본에 역반영하지 않는다. 출력이 기준 버전과 다르면 충돌로 보고하고, 사용자가 그 변경을 원본에 가져올지 결정한다.

| 단위 | 책임·입출력 | 의존 대상 |
| --- | --- | --- |
| 대상 선택·가져오기 | 선택 경로를 읽어 자산 목록과 원본 후보를 만든다. 기본 동작은 읽기다. | 파일 시스템, 명시한 범위 |
| 원본 검증 | 문서 참조·스킬 구조·도구별 차이를 검사한다. | 자산 목록, 지원 규칙 |
| 대상별 출력 | 원본을 Claude·Codex에 맞는 파일 집합으로 계산한다. | 원본과 도구별 설정 |
| 변경 계획 | 출력 예정 파일, 현재 파일, 이전 적용 기록을 비교한다. | 대상별 출력, 파일 해시 |
| 적용·복구 | 검토한 계획의 전제조건을 재확인하고 기록·백업과 함께 반영한다. | 변경 계획, 파일 시스템 |
| 플러그인·CLI 진입점 | 사용자가 범위·diff·오류를 이해하고 작업을 실행하게 한다. | 같은 실행 엔진 |

이는 책임 구분이며 각각을 별도 패키지로 만들겠다는 결정은 아니다. 구현 시 필요한 파일 수와 의존성을 줄인다.

## 충돌과 실패 정책 제안

- 관리 대상 밖의 파일은 수정하거나 삭제하지 않는다. 같은 이름의 기존 파일도 최초 가져오기에서 소유권을 확인하기 전에는 덮어쓰지 않는다.
- 이전 적용 내용과 실제 출력이 다르면 충돌로 표시한다. 첫 버전에서는 자동 병합보다 중단과 diff를 우선한다.
- 변경 계획 이후 파일이 바뀌면 적용을 중단하고 새 계획을 요구한다. 검토한 내용과 적용 내용이 달라지는 것을 방지한다.
- 같은 원본을 다시 적용하면 변경이 없어야 한다. 원본에서 빠진 파일의 삭제는 일반 갱신과 구분해 검토한다.
- 지원하지 않는 메타데이터·지시·참조는 파일별로 보고한다. 기능이 유지되는지 모르는 변환을 성공으로 처리하지 않는다.
- 경로 탈출과 관리 범위 밖을 가리키는 심볼릭 링크는 검사한다. 충돌 비교와 쓰기 직전에 대상 경로를 다시 확인한다.
- 여러 파일을 쓰다 실패할 수 있으므로 파일 단위 교체만으로 전체 작업의 원자성을 주장하지 않는다. 적용 기록으로 중단 지점을 추적하고 복구 절차를 검증한다.
- 복구 이후 생긴 사용자 수정을 덮어쓰지 않도록 복구 시점에도 해시를 검사한다. 자동 복구가 불가능하면 필요한 수동 조치를 표시한다.

## 구현 전 검증과 개발 순서

| 단계 | 산출물 | 통과 기준 |
| --- | --- | --- |
| 1. 사용 범위 합의 | 최초 사용 시나리오와 범위 결정 | 전역·프로젝트, 한 기기·여러 기기, 원본 편집 위치가 정해진다. |
| 2. 호환성 실험 | 임시 프로젝트의 공통 스킬 1개·공통 지침 1개·도구 전용 항목 1개 | Claude·Codex가 기대한 파일을 발견한다. 도구 전용 항목의 차이를 기록한다. 지원 버전을 기록한다. |
| 3. 읽기 전용 엔진 | 대상 선택·검증·변경 계획 | 실제 설정을 수정하지 않고 추가·변경·삭제·충돌·미지원을 구분한다. |
| 4. 적용·복구 엔진 | 적용 기록·백업·충돌 중단·복구 | 반복 적용에서 변경이 없고, 중간 실패와 사용자 수정이 있는 상태에서 데이터 보존을 검증한다. |
| 5. 두 플러그인 연결 | Claude·Codex 진입점 | 각각 설치 후 같은 엔진으로 같은 계획을 만들고 검토·적용 흐름을 실행한다. |
| 6. 첫 버전 범위 재검토 | 설치·사용 문서와 확인된 제약 | 합의한 사용 시나리오를 실제 두 도구에서 재현한다. 이후 전역·다중 기기 지원 여부를 결정한다. |

기간은 아직 추정하지 않는다. 2단계에서 문서 탐색과 플러그인 설치의 실제 제약을 확인한 뒤 남은 작업량을 산정한다.

## 검증 시나리오

| 상황 | 관찰할 결과 |
| --- | --- |
| 공통 스킬 최초 반영 | 본문·참조·상대 경로가 보존되고 두 도구에서 스킬을 발견한다. |
| 공통 지침 수정 | 두 출력에 같은 공통 내용이 반영되고 도구별·사용자 작성 내용이 남는다. |
| 변경 없이 재적용 | diff가 비어 있고 불필요한 재쓰기가 발생하지 않는다. |
| 대상 파일 수동 수정 | 충돌을 보고하고 자동으로 덮어쓰지 않는다. |
| 계획 이후 파일 수정 | 오래된 계획 적용을 중단한다. |
| 기존 스킬과 이름 충돌 | 중복 또는 충돌을 표시하고 사용자가 선택하기 전에는 덮어쓰지 않는다. |
| 원본에서 파일 제거 | 삭제 예정 파일과 이유를 표시하며 관리 밖 파일은 보존한다. |
| 도구 전용 지시·누락 참조 | 문제가 있는 파일과 사유를 보고한다. 의미 보존을 확인하지 못한 변환은 중단한다. |
| 적용 도중 쓰기 실패 | 부분 적용 상태를 식별하고 복구 경로를 제공한다. |
| 적용 후 수정한 파일 복구 | 새 사용자 변경을 보존하고 충돌을 표시한다. |

계산 로직은 테스트용 파일로 검증하고, 파일 적용은 임시 디렉터리에서 실패 상황까지 검증한다. 최종 호환성은 실제 Claude Code와 Codex에서 설치·탐색·호출을 관찰한다. Markdown 내용의 일치나 테스트 통과만으로 모델의 동작까지 같다고 결론 내리지 않는다.

## 다음 논의에서 정할 것

첫 질문은 **한 컴퓨터의 Claude ↔ Codex 동기화부터 시작할지, 여러 컴퓨터까지 포함할지**다. 추천은 한 컴퓨터부터 시작하는 것이며, 이는 확정된 범위가 아니다.

그다음에는 다음 순서로 결정한다.

1. 개인 전역 설정과 프로젝트 설정 중 실제로 더 자주 어긋나는 쪽을 먼저 다룬다.
2. 공통 원본을 직접 편집하는 흐름을 받아들일지, 기존 Claude 또는 Codex 파일을 원본으로 유지할지 정한다.
3. 첫 실험에 사용할 실제 스킬·지침 사례를 선정한다. 필요한 기능 차이를 기준으로 지원 범위를 좁힌다.
4. 실험 결과를 보고 실행 언어·설치 방식·최소 지원 버전을 정한다.

아직 검증하지 않은 항목은 실제 두 도구의 플러그인 설치 흐름, 도구 전용 메타데이터의 변환 가능 범위, 관리 구간과 기존 지침의 우선순위 상호작용, 다중 파일 복구 방식이다. 위 구현 전 실험과 검증 시나리오로 확인한다.
